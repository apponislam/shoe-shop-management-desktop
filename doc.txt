# Shoe Shop Management — Development Prompt

I am building a **Windows offline desktop Shoe Shop Management / POS application**.

The application must work completely offline. There should be **no Express backend, no cloud API, no MongoDB, and no PostgreSQL server**.

## Technology Stack

Use exactly:

* Electron
* React
* TypeScript
* Vite
* Tailwind CSS
* shadcn/ui
* Lucide React
* Recharts
* Prisma ORM
* SQLite
* Electron IPC
* Secure Electron preload
* electron-builder
* ESLint

Architecture:

```text
React + TypeScript + Vite
        ↓
      Electron
        ↓
Electron Main Process
        ↓
      Prisma
        ↓
      SQLite
```

React must **never import Prisma directly**.

Use:

```text
React
  ↓
preload.ts
  ↓
Electron IPC
  ↓
main.ts
  ↓
Prisma
  ↓
SQLite
```

Use `contextIsolation: true` and `nodeIntegration: false`.

# Important Architecture Rules

Follow these rules throughout the entire project.

### 1. No backend server

Do NOT create:

```text
Express
Fastify
NestJS
```

Electron main process handles backend-like operations.

### 2. No cloud database

Do NOT use:

```text
MongoDB
PostgreSQL server
MySQL
Firebase
Supabase
```

Use:

```text
SQLite + Prisma
```

### 3. Secure Electron

Use:

```ts
contextIsolation: true
nodeIntegration: false
```

Use `contextBridge` and IPC.

### 4. Database access

React must never do:

```ts
import { PrismaClient } from "@prisma/client";
```

All Prisma operations belong to Electron's main process.

### 5. Transactions

Sales, purchases, payments, and stock changes must use database transactions where appropriate.

For example:

```text
Complete Sale
 ├── Create Sale
 ├── Create Sale Items
 ├── Create Payment
 ├── Decrease Stock
 └── Create Stock Movements
```

Either everything succeeds or the transaction rolls back.

### 6. Don't over-engineer

This is an **offline single-shop desktop application**.

Do not add unnecessary:

* Microservices
* REST APIs
* Cloud infrastructure
* Redis
* WebSockets
* Kubernetes
* Docker
* External authentication services

Keep the architecture simple, reliable, and maintainable.

### 7. UI

Use:

* Tailwind CSS
* shadcn/ui
* Lucide React

Avoid creating unnecessary custom UI components when shadcn/ui already provides the component.

### 8. Code quality

Use:

* TypeScript
* Strong typing
* Reusable components
* Clean folder structure
* Clear service boundaries
* Proper error handling
* Loading states
* Empty states
* Confirmation dialogs for destructive actions
* Form validation

### 9. Development discipline

Implement **one step at a time**.

Do not jump ahead.

After completing each step:

1. Run the application.
2. Test the functionality.
3. Fix errors.
4. Confirm the step works.
5. Only then continue to the next step.

Do not modify working features unnecessarily when implementing a new step.
